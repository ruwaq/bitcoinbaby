## CRITICAL

### 1. Hardcoded Testnet Private Key in 3 Script Files

**Files:**
- `packages/bitcoin/scripts/debug-keys.ts:12`
- `packages/bitcoin/scripts/live-mining-test.ts:30`
- `packages/bitcoin/scripts/test-mint-babtc.ts:30`

**Match:** `TESTNET_PRIVATE_KEY = "17204f40409a85b8a9b7a4b7bb1081917adf770779c2e55959e14e9da62a766b"`

**Analysis:** These are testnet keys used for debugging and testing scripts. While they're on testnet4 (no real value), the pattern is dangerous if accidentally copied to mainnet code. The same key is duplicated across 3 files. Additionally, the debug-keys.ts script logs the derived address and public key at lines 20-54.

**Severity: CRITICAL** (security risk, even for testnet)

**Fix:**
- Move private keys to `.env` or environment variables
- Document these as test-only keys explicitly with big warnings
- Use a different key per script to limit blast radius
- Add a pre-commit hook that rejects hex strings matching private key patterns

```typescript
// Instead of:
const TESTNET_PRIVATE_KEY = "17204f...";

// Use:
const TESTNET_PRIVATE_KEY = process.env.TESTNET_PRIVATE_KEY;
if (!TESTNET_PRIVATE_KEY) throw new Error("TESTNET_PRIVATE_KEY not set");
```

### 2. `new Function()` for Dynamic Import in Production

**File:** `packages/core/src/mining/ai-integration.ts:147`

```typescript
// eslint-disable-next-line @typescript-eslint/no-implied-eval
const importFn = new Function("p", "return import(p)");
const aiModule = await (importFn as (p: string) => Promise<any>)(
  packageName,
);
```

**Analysis:** This uses `new Function()` to dynamically import the `@bitcoinbaby/ai` package. The eslint comment acknowledges it's an `eval`-like pattern. The code is wrapped in try/catch (line 140) and the AI module is optional. However, `new Function()` is an execution vector — if the package name were somehow user-influenced, this would be a code injection vulnerability. Currently safe since `packageName` is a hardcoded constant.

**Severity: CRITICAL** (code injection vector, even if currently safe)

**Fix:**
```typescript
// Use proper dynamic import with @ts-expect-error or a type assertion
const aiModule = await import(/* @vite-ignore */ "@bitcoinbaby/ai") as typeof import("@bitcoinbaby/ai");
```

Or better, restructure to use conditional import with build-time tree shaking.

### 3. Type Safety Loss (`mempoolService as any`) in Critical Claim Route

**File:** `apps/workers/src/routes/claim.ts:284, 347`


**Analysis:** The `createPsbtBuilder` function expects `IMempoolService` but the return of `initMempoolService` doesn't match the interface exactly, so `as any` is used. **Fix:**
- Fix `initMempoolService` to return the proper `IMempoolService` type
- Or add a type assertion to `IMempoolService` instead of `any`
- Or create an adapter that wraps the return value

### 4. Floating Promise: Non-blocking API Calls Without Error Recovery

**File:** `apps/web/src/hooks/useMintNFT.ts`

Multiple instances of fire-and-forget API calls using `.catch()` only for logging:

```typescript
// Line 311-315: Update attempt status to proving
apiClient
  .updateMintAttempt(attemptId, "proving")
  .catch((err) => log.warn("Failed to update attempt:", { error: err }));

// Line 395-399: Update attempt status to signing
apiClient
  .updateMintAttempt(attemptId, "signing")
  .catch((err) => log.warn("Failed to update attempt:", { error: err }));

// Line 468-472: Update attempt status to broadcasting
apiClient
  .updateMintAttempt(attemptId, "broadcasting")
  .catch((err) => log.warn("Failed to update attempt:", { error: err }));

// Line 565: Confirm NFT mint (NON-BLOCKING - commented as such)
apiClient
  .confirmNFTMint(reservedTokenId, broadcastSpellTxid, wallet.address, nftData)
  .catch((err) => log.warn("Failed to confirm mint:", { error: err }));

// Line 569-576: Update attempt to confirmed
apiClient
  .updateMintAttempt(attemptId, "confirmed", { ... })
  .catch((err) => log.warn("Failed to update attempt:", { error: err }));

// Line 600-604: Update attempt to failed
apiClient
  .updateMintAttempt(attemptId, "failed", { error: message })
  .catch((updateErr) => log.warn("Failed to update attempt:", { error: updateErr }));

// Line 612-619: Release reserved token ID
apiClient
  .releaseNFT(reservedTokenId)
  .catch((releaseErr) => log.warn("Failed to release token:", { error: releaseErr }));
```

**Analysis:** These are intentionally non-blocking calls (commented as such in the code for confirmNFTMint at line 557). The pattern is correct for not blocking the main flow, but:
- If `updateMintAttempt` fails silently, the attempt state becomes stale in the tracking system
- If `releaseNFT` fails, the token ID is permanently reserved with no way to recover
- No retry mechanism exists — if the network blips, these calls are lost forever

**Severity: HIGH** (can cause stuck reservations and stale state)

**Fix:**
- Add exponential backoff retry with a max of 3 attempts
- For `releaseNFT`, consider using a timeout queue that periodically retries
- Add an `onError` callback to surface these failures to the user if critical

## Architecture Review: Transaction Flow Safety

### Claim Flow (claim.ts + PSBT builder)

**Flow:** GET balance → POST execute → POST complete
**Assessment:** GENERALLY SAFE

- Address validation with regex on all endpoints
- Rate limiting applied to all claim routes
- Proper error handling in PSBT build/finalize
- Network validation (`validateAddressNetwork`)
- **ISSUE:** `mempoolService as any` bypasses type safety (Critical #3)
- **ISSUE:** The `complete` route broadcasts but doesn't wait for confirmation — relies on polling `/status/:claimId` which returns hardcoded `"processing"` (claim.ts:408)

### Mint Flow (useMintNFT.ts)

**Flow:** Reserve tokenId → Generate traits → Submit to prover → Sign → Broadcast
**Assessment:** GENERALLY SAFE with concerns

- Health check before starting (optional, fails gracefully)
- UTXO validation with minimum threshold (2000 sats)
- Token ID release on error
- Detects PSBT vs raw transaction format
- **ISSUE:** Multiple fire-and-forget API calls (see #4)
- **ISSUE:** Token ID release is itself fire-and-forget — if it fails, token is permanently stuck
- **ISSUE:** No timeout on prover API calls

### Marketplace Flow (useMarketplace.ts)

**Flow:** List (PSBT-based) → Buy (PSBT atomic swap)
**Assessment:** GENERALLY SAFE

- PSBT-based atomic swap for buy/sell
- Uses SIGHASH_SINGLE|ANYONECANPAY for partial signing
- Dynamic fee rate estimation
- Legacy fallback path when seller PSBT is missing
- **ISSUE:** Trusts the listing PSBT from the server — a compromised server could craft a PSBT that steals funds
- **ISSUE:** No validation that the seller actually owns the NFT before listing

### Treasury Signing (treasury-signer.ts)

**Flow:** Poll → Prepare spell → Sign → Broadcast commit → Broadcast spell → Confirm
**Assessment:** NEEDS ATTENTION

- Proper start/stop with cleanup
- Wallet from mnemonic (secure)
- Prover-based spell signing
- **ISSUE:** TODO at line 367 indicates PSBT signing not fully implemented
- **ISSUE:** 2-second sleep between commit and spell broadcast (line 283) — not sufficient for network propagation

## Methodology

The scan was performed using a Python regex-based scanner (`/tmp/bug_scan.py`) that:

1. Recursively walks all `.ts`/`.tsx` files in the project
2. Excludes `node_modules`, `.next`, `dist`, `.git`, `coverage`, `.turbo`
3. Skips test files (`*.test.*`, `*.spec.*`) for production patterns (console.log, `as any`, `: any`, non-null assertions)
4. Includes test files for bug patterns (empty catch, floating promises, eval, hardcoded secrets)
5. Applies heuristic severity adjustment (e.g., checking if JSON.parse is wrapped in try/catch, checking if setInterval has corresponding clearInterval)
6. Each finding was manually reviewed with 5 lines of context to determine if it's a real bug or false positive
7. Special attention was paid to `apps/web/src/hooks/` (29 files) and `apps/workers/src/` (56 files) as the core transaction and state management code
